## The problem: two representations of one calibration

Parameter estimation with the PEST family of software — PEST (Doherty 2015), PEST_HP, and PEST++ (White et al. 2020) — is now routine in groundwater modeling. Every PEST run is defined by a control file: a text document that lists parameters and their bounds, observations and their weights, parameter and observation groups, prior information, the model command, and the template and instruction files that connect PEST to the model. For a highly parameterized model this file runs to tens of thousands of lines.

Nobody writes such a file by hand, and in consulting practice it is rarely generated by a script alone either. The working record of a calibration usually lives in a spreadsheet. A workbook holds one sheet per parameter type, an observation sheet per data source, helper columns that carry model layer or pilot-point indices, and formulas that compute observation weights — balancing groups against one another, down-weighting a period of record, scaling a bound from a native value. That workbook is what colleagues review, what clients are shown, and what carries the run history in its notes. The control file is derived from it.

The derivation is where things go wrong. Counts in the control file's header must match the tables exactly; parameter groups must be defined before they are used; a tied parameter must point at a parameter that exists and is not itself tied or fixed; a regularization equation must not cite a fixed parameter; every parameter must appear in a template file and every observation in an instruction file. PEST reports each of these as a fatal error at start-up, which is tolerable, or as silently wrong behavior, which is not. And after a run the traffic reverses: best parameter values, residuals, and — for PESTPP-IES — a chosen realization must go back into the workbook, by name, into the right rows of the right sheets, without overwriting the formulas that produced the weights in the first place.

The author's own experience motivated the tool described here. A conversion script that had produced control files for a regional model through more than a dozen calibration runs turned out, on review, to have silently dropped one control variable (the Jacobian-update setting the modeler had set in the workbook) and to have rounded every parameter and observation value to six significant figures. Neither error stopped PEST. Both were invisible in a 40,000-line text file. What was missing was not a converter — pyEMU (White et al. 2016) can write a control file from a DataFrame — but a layer that treats the spreadsheet and the control file as two views of the same calibration and keeps them provably consistent in both directions.

## What makePst does

makePst (installed and invoked as `makepst`) is an open-source Python package (MIT license) with a command-line interface. It requires only pandas and openpyxl; Excel itself is optional. Its central object is a `Pst`: the parameter, observation, group, and prior-information tables as DataFrames, plus the control variables, model command lines, template and instruction pairs, and PEST++ `++` options. Everything flows through that object, so one set of validation rules applies whichever direction the data travels. Seven commands cover the workflow (Figure 1).

**`build`** reads sheets from an Excel workbook (or CSV files) and writes the control file. Tables may be split across any number of sheets — eight parameter sheets and seven observation sheets in the demonstration below — and a sheet name may be a glob (`PAR_*`). Column headers are the PEST variable names, so a sheet is readable without documentation; any other columns are ignored, which is what makes helper columns and formulas harmless. A `CONTROL` sheet lists control variables by name; whatever is blank takes the PEST default. All counts (`NPAR`, `NOBS`, `NOBSGP`, `NTPLFLE`, …) are computed, never typed. In regularization mode a `PRIOR` column on the parameter sheet generates the prior-information equations: a number gives a preferred value, another parameter's name gives an equality constraint, with `log()` applied according to each parameter's transformation. PEST_HP keywords such as `win_mrun_hours` and per-group `absparmax(n)` limits, and PEST++ options, are written as given. The command line that builds a workbook can itself be stored in the workbook (a `BUILD` sheet), after which `makepst build project.xlsm` is the whole recipe.

**`validate`** is a pestchek-style report that changes nothing. Beyond the table checks — duplicate names, undefined groups, bad ties, initial values outside bounds, malformed or mistyped prior equations, PEST's name-length limits — it opens the template and instruction files and cross-checks them: every parameter cited somewhere, every observation read exactly once, no names that the control file does not know. Optionally it runs each instruction file against the model's output file with a small interpreter that follows the PEST manual, which catches the classic mistake of a whitespace instruction too few. It accepts a workbook directly, so a setup can be checked before any control file exists, and it exits with a nonzero status so a batch file can stop.

**`dump`** does the reverse of `build`: it reads a control file — classic or PEST++ version 2 with external tables — into a workbook whose sheets `build` can read back, including the `BUILD` sheet. This is how an inherited control file enters the spreadsheet workflow, or how a lost workbook is recovered.

**`update`** returns results to an existing workbook. Given a `.par` file, a residuals file, or PESTPP-IES parameter and observation ensembles (with a realization chosen by name or as the lowest-phi member of the iteration), it finds every worksheet with a `PARNME` or `OBSNME` column, matches rows by name, and writes only the requested columns. Cells that hold formulas are left alone unless the user says otherwise. Two backends exist: openpyxl, which needs no Excel and keeps macros but drops charts; and xlwings, which drives Excel itself so that everything in the workbook survives and formulas recalculate. With residuals available, `update` also writes a `PHI` sheet — the objective function by observation group, as PEST prints it at the end of a run — and, for an ensemble, the phi of every realization.

**`parrep`** replicates PEST's PARREP utility: parameter values from a `.par` file or an IES realization into a new control file, optionally changing control variables on the way (`--set noptmax=0` for a final run), with the base being either a control file or the workbook that built it.

**`diff`** compares two control files, or a control file and a workbook, semantically: parameters and observations added, removed, or changed column by column; prior equations; effective control values; options; file pairs. Numbers are compared to a tolerance, so reformatting is not a change. **`init`** writes a starter workbook — every sheet with the expected headers, every control variable with its default and a one-line description, drop-down lists where PEST allows only fixed words, and a `BUILD` sheet — that builds a valid control file as it is.

Two further design decisions matter for auditability. Every command that produces a file writes a sidecar manifest beside it: the package version, the exact command line, the SHA-256 hash and sheets read from every input, and the hash and section counts of the output. A control file can therefore be traced to the precise workbook that made it, and a hash mismatch says the two have diverged. And round-tripping is defined precisely: reading a control file and writing it again is an identity, and `dump` followed by `build` reproduces the same text. What is normalized (names lower-cased, as PEST treats them; numbers to 11 significant figures) and what is dropped (unrecognized sections, with a warning) is documented, not discovered.

## Demonstration on a regional model

The demonstration uses the calibration workbook of a regional transient MODFLOW model from a consulting project (details withheld; the numbers below are as reported by the software). The workbook has 19 sheets that makePst reads: a `CONTROL` sheet, a group sheet, eight parameter sheets (hydraulic conductivity, vertical conductivity, storage, specific yield, stream conductance, boundary heads, recharge multipliers, and miscellaneous), seven observation sheets (steady-state and transient heads, head differences, flows, leakage, and lake stages), an input/output sheet, and two PEST++ option sheets. Many observation weights are formulas that look up the number of records per well and a group-balancing factor. All timings are on a laptop (Windows 11, Python 3.12) and are wall-clock.

*Build.* One command produces a 2.6-MB control file of 43,575 lines: 1,068 parameters in 12 groups, 41,747 observations in 12 groups, 185 regularization equations generated from the parameter sheets, 18 template and 7 instruction files, in 7–12 s depending on machine load, most of it spent reading Excel. The manifest records the workbook's hash and all 19 sheet names.

*Round trip.* `dump` writes the control file to a fresh workbook in 2–6 s; `build` from that workbook's `BUILD` sheet takes 2–5 s; `diff` between the original and the rebuilt control file reports no differences. The two files are byte-identical.

*Against the legacy script.* `diff` between the control file the old script had produced for the same run and the new one reports 479 parameter values and 16,134 observation values changed at a tolerance of 10⁻⁹ and none at 10⁻⁵ — the six-significant-figure truncation — plus one control variable, `JACUPDATE`, present only in the new file. This is the kind of finding the tool exists to make visible.

## Validation, scope, and limitations

The package ships with 95 automated tests that run on Linux and Windows for Python 3.9 through 3.13 (pandas 2.3 and 3.0). They include golden-file builds from a synthetic workbook laid out like the demonstration's, the read–write identity, byte equality of `dump` followed by `build`, workbook updates with multi-sheet matching and formula protection, IES realization selection, the control-section parser, every validation rule, the instruction interpreter, and the tutorial in the documentation, which is executed verbatim. Two tests run the demonstration model when its files are present.

makePst reads and writes the classic control-file format and PEST++ version 2 (keyword control data and external CSV tables), and reads `.par`, `.res`/`.rei`, and PESTPP-IES `par.csv`, `obs.csv`, and `phi.actual.csv` files. It does not perform calibration, uncertainty analysis, geostatistical parameterization, or run management; those are PEST's and pyEMU's business. The instruction interpreter behind `validate --outputs` follows the manual but is not PEST, and its findings are reported as warnings; the documentation recommends running pestchek on every generated file regardless. Sections makePst does not model (predictive analysis, Pareto, sensitivity reuse, derivatives command line) are kept verbatim; anything unrecognized is dropped with a warning that names it. Excel-faithful updates require Excel and xlwings; the openpyxl backend keeps macros but not charts or images, and formula results are stale until Excel next opens the file.

The relationship to pyEMU deserves a precise statement. pyEMU's `Pst` object also reads and writes control files, and a `makepst` bridge converts in both directions. The test suite pins what that round trip loses: parameters, observations, priors, and `++` options survive; PEST_HP keyed tokens, header comments, and the regularization section (which pyEMU rewrites with its own defaults) do not. That is a statement about scope, not quality — pyEMU models PEST++ — and it is why the two are complementary: makePst is the interchange and audit layer for the workbook, pyEMU the analysis toolkit.

## Significance for practice

The immediate benefit is reproducibility. A calibration defined by a workbook and a one-line command can be rebuilt, on another machine and by another person, and shown by `diff` to be the same. The manifest makes the claim checkable after the fact, which matters when a model is reviewed by a client or an agency years after the run.

The second benefit is that the review artifact and the executable artifact stop drifting apart. Modelers can keep doing what they already do — weighting in formulas, annotating in notes, splitting parameters across sheets by type — and still get a control file that PEST accepts on the first try, with the name-level errors caught before a run rather than after. Results come back into the same workbook without a copy-and-paste step, so the workbook remains the record of the calibration rather than a record of its starting point.

Finally, because CSV is accepted everywhere a sheet is, the same workflow runs without Excel in a continuous-integration job or on a cluster. The likely users are consulting and agency modelers who run PEST-family software and keep their projects in spreadsheets; educators may find the starter workbook and the `validate` report a gentler introduction to the control file than the manual.

By treating spreadsheets and control files as synchronized views of one calibration configuration, makePst lets groundwater modelers retain familiar review practices while making control-file construction, checking, and result transfer reproducible. It is intended as a small, auditable layer within existing PEST and PEST++ workflows, not a replacement for any part of them.
